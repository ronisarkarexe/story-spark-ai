## Getting Started Early

Experience shows that the best thing to help your application is to **contact the organization early**.

- Introduce yourself on the organization's communication channels (mailing list, chat, discussions).
- Find and fix a small bug or tackle a beginner issue.
- Refer to the official Open Source Guides for introductory contributing tips.

---

## Am I Experienced Enough?

The answer is generally: **Yes!**

- We value **creativity, intelligence, and enthusiasm** above specific knowledge of the libraries or algorithms used.
- An interested and motivated contributor willing to learn is more valuable than pre-existing domain expertise.
- Available projects cater to various background levels.
- If you have prior experience with the project technology stack or dependencies, highlight it in your application.

## Our Expectations From Contributors

### During the Application Phase

Organizations favor contributors who demonstrate **regular, meaningful communication** with mentors and the community leading up to accepted project announcements.

Good communication establishes:
1. **Reliability**: Proves you are active and accountable.
2. **Communication Skills**: Crucial for asynchronous remote mentorship.

---

### Evaluation Point System

When evaluating applications, maintainers use the following scoring baseline:

| Criteria | Points | Notes |
| :--- | :---: | :--- |
| **Communication with Mentors** | `5 pts` | Active discussion with potential project mentors |
| **Community Engagement** | `5 pts` | Active participation in community channels / discussions |
| **Referenced Code & Portfolio** | `5 pts` | Links to prior code, repositories, or pull requests |
| **Contact Methods** | `5 pts` | Provide multiple contact channels (Email, GitHub, Chat, etc.) |
| **Preliminary Project Plan** | `3 pts` | Timeline overview (Before, During, After GSoC) |
| **Project Selection & Motivation** | `3 pts` | Clear rationale for chosen project and completion feasibility |
| **Time Commitment** | `3 pts` | Explicit statement of available time and listing existing commitments |
| **Cloud Link to Application Files** | `1 pt` | Public link (GitHub/Dropbox) to application documents |
| **Karma Points** | `0 pts` | Honesty and transparency |
| **Pull Request on Existing Code** | `5 pts` | Submitted PR on existing codebase before selection |
| **Continued Communication** | `5 pts` | Sustained engagement until accepted projects announcement |

### During the Summer

These requirements apply to accepted contributors during the GSoC coding period:

#### 1. Communication
- **Bi-weekly Blog**: Publish a short blog post report every 2 weeks.
- **Commit Early & Often**: Push commits regularly to public repositories (e.g., GitHub) for review.
- **Community Bonding**: Actively work on timeline preparation and engage during bonding period.
- **Daily Communication**: Check in every working day with your mentor in public channels.
- **Advance Notice**: Inform mentors immediately if personal circumstances prevent regular work.

> ⚠️ **Note**: Failure to maintain regular communication may result in failing evaluations.

#### 2. Evaluations
- Set **realistic, achievable milestones** for evaluation deadlines.
- Have at least **one public commit reviewed** prior to each evaluation phase.
- **Hard Requirement**: Have at least **one commit merged into the main development branch** before final evaluation.

#### 3. Blogging
- Keep a journal of your contributor journey and post blog updates at least once every 2 weeks.

## Default Instructions & Idea List

- **Idea List**: Review proposed project ideas listed on the organization's ideas page.
- **Custom Proposals**: You may propose custom project ideas, but you **must contact the organization beforehand** and secure an assigned mentor. Proposals without a mentor will not be considered.

---

## How to Write a Great Proposal

1. **Choose Wisely**: Pick a project you are genuinely interested in working on for several months.
2. **Understand Scope**: Ensure you grasp the technical requirements and user expectations.
3. **Contact Early**: Solicit early feedback from mentors to iteratively improve your draft.
4. **Original Solutions**: Propose thoughtful solutions and architectural ideas.
5. **Technical Detail**: Detail your technical approach, implementation plan, and edge-case handling.

---

## Dividing Your Project

To satisfy the requirement of merging code into the main development branch before the summer ends:

- Break your project into **small, self-contained subprojects**.
- Target merging at least one subproject around **Phase 2 evaluations**.
- Submit bug fixes or refactoring PRs encountered during development as independent, focused pull requests.

---

## How to Estimate Time Needed for Development

1. **Hands-on Practice**: Fix an easy bug or refactor existing code to familiarize yourself with style guidelines and architecture.
2. **API & Interface Planning**: Design public APIs, class structures, and draft pseudocode algorithms before estimating effort.
3. **Conservative Estimates**: Account for academic exams, holidays, and unforeseen technical blockers.
4. **Buffer Time**: Include extra time for PR code reviews, revision cycles, and CI testing.

---

## Final Proposal Submission

- **File Format**: Submit final proposal as a **PDF file** to the GSoC portal.
- **Naming Convention**: Prepend filename with `[sub-org-name]`, e.g.:
  `[SubOrgName]_GSoC_2026_Proposal_ContributorName.pdf`
